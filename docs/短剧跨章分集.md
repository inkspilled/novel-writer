# 短剧跨章分集

「短剧 → 智能分集」提供“生成下一集”与“持续分集”两种范围。旧的逐章转剧本入口保留。

每轮从未使用的素材中读取最多 5 章，单轮原始素材最多 50,000 字符（`MAX_SOURCE_CHARS`，超出就缩小窗口，不会把一章拆开）。**送进模型的不是正文，而是工作流已经产出的结构化中间物**：细纲、章概要、章后抽取五段、角色推演、故事线台账；原文只在对白/动作需要核对时切片补一小段。模型先输出本集标题、目标、钩子、剧情节拍和来源章节，再把选定素材的简报与对白切片交给编剧生成场次剧本。

例如先读第 1–5 章，规划选取第 1–4 章生成第 1 集：第 5 章保持待用，下轮补读第 6–9 章。模型只能选取阅读窗口的连续前缀，不能跳章或重复消费；只有剧本成功保存后才确认来源映射。素材不足时可标记等待后续正文，不强行成集。

## 上下文切片（`core/drama_context.py`）

写小说时每一步都在产出可复用的结构化数据（细纲 / 概要 / digest 五段 / 角色推演 / 故事线台账）。短剧改编没有理由再从零读一遍正文——那既贵，又让模型把已经想清楚的东西重新解释一遍。所以按「信息密度 / 成本」分层取用：

| 层 | 来源 | 用途 | 预算 |
|---|---|---|---|
| 1 | `planning/章节细纲.md` 本章节 | 事件、转折、钩子（分集与编剧的主依据） | 520/章 |
| 2 | `chapters/{n}_*.summary.md` | 章概要（细纲缺失时的主依据） | 260/章 |
| 3 | `digest/{n}.json` | summary / percept 事件 / threads 推进 | 事件 6 条、线程 4 条 |
| 4 | `sim_cache/sim_{n}.md` | 角色推演：谁想要什么、准备怎么做 | 300/章 |
| 5 | `story_threads.json` | 进行中的主线/支线、待回收伏笔 | 260/章 |
| 6 | **跨章 RAG（全库，只查已发生章节）** | 人物首次登场、伏笔埋设、旧冲突与承诺 | 2,400/集 |
| 7 | 本集正文 | 只取对白/动作密度最高的场景，核对台词与可拍动作 | 每集约 4,000–5,000 |

单章简报 `chapter_brief()` 合计 900 字；没有第 1–5 层数据的老项目自动回退到原文切片（`slice_chapter`），不会因为没跑过工作流就不能改编。

### 第 6 层：短剧的「大量检索」用在这里

简报只覆盖本集素材的那几章，但一集里经常要接「第 3 章埋的伏笔、第 12 章才回收」「这个角色第 8 章第一次出场」这类跨章长尾。这些按章读全文太贵，交给 RAG：

- **多路查询**：集名 / 细纲摘要 / 出场人物名 / 本集目标与钩子，各查一次，合并去重；
- **只查已发生章节**：`load_chapters(before_chapter)` 把检索上限钉在本集来源章之前，**绝不把还没写到或还没改编的后续剧情漏进提示词**（防剧透，也防模型提前用掉反转）；
- **只注入前 4–6 条**：单块截 600 字，合计 2,400 字，避免把检索结果又变成第二个「整本塞」；
- **有 embedding 就用**：配了 embedding 时走「BM25 + 语义」RRF 融合（本地 Qwen3-Embedding 一次检索约 0.3s），没配或失败时自动回退纯 BM25；
- 配了重排模型时仍会精排。

检索由 `retrieve_prior()` 完成，底层用 `RAGRetriever.search_chunks()`（返回块与分数，方便上层去重/拼装，`retrieve()` 仍是它的格式化版本）。

切片本身的经验规则不变：

| 规则 | 做法 |
|---|---|
| 预算内不切 | 文本没超预算就原样送，不做无谓的信息损失 |
| 按场景切 | 超预算时复用 RAG 的场景分块（`rag_chunking.chunk_chapter`），一场戏不会被拦腰截断 |
| 冲突密度优先 | 冲突/反转/决定类词、对白行、出场人物越多得分越高；铺陈、抒情、设定说明先被丢 |
| 首尾必留 | 开场块和最后一块先占预算（承载入戏与集尾钩子） |
| 原序拼接 | 选中的块按原文顺序还原，块间标「（略）」，提示模型不要补写被略过的剧情 |

预算（字符）：分集策划窗 9,000（有简报时按简报，实测 4.6 万字窗口 → 约 600 字简报）；单集剧本 6,000（简报 + 对白切片）；原文兜底 12,000；改编圣经 6,000、单份规划文档 2,600；分镜剧本 12,000；上一集结尾 900。

其它切片：

- **改编圣经**按 Markdown 小节选：优先「红线 / 规则 / 节奏 / 钩子 / 视觉锚点」相关小节，其余按预算截断。
- **人物档案**只留本章/本集出场的人（角色名从正文匹配），一个都没匹配上才退回按预算切片。
- **分镜**超预算时压动作描述、保全部 `## 场次` 标题与台词，镜头表不会缺场。
- **前情**只回看最近 3 集的「集名 / 目标 / 钩子」+ 上一集结尾 900 字，不整段回读。

Worker 每次调用会往日志里写一行切片账单（原文多少字 → 送入多少字、用的是简报还是原文兜底），便于核对成本和是否漏料。

## 数据与恢复

- `drama/episodes.json`：每集的 `source_chapters`、`source_hashes` 与 `adaptation_plan`；这是素材是否已使用的权威来源，兼容旧 `source_chapter`。
- `drama/adaptation.json`：待用章节、最近阅读窗口和顺延原因，是可重建的状态快照。
- `drama/episodes/epNNN.md`：剧本；写入成功才提交来源元数据。元数据写入失败则回滚主剧本，生成稿保留为 `.pending.md`。
- 恢复时从来源映射重新计算未用素材，避免因停止或旧快照重复生成。旧项目已经关联的章节也算已用。
- 已改编源文的指纹变化、已用素材中间出现缺口时，停止自动续接并提示复核，防止新旧剧情混用或次序颠倒。

剧本页显示来源章节；顶部概览显示待用章节，悬浮可查看顺延原因。小说正文不被改写；逐章生成不能覆盖已经合并多章的剧集。

## 边界

当前**素材单位**仍是完整章节，支持多章合一集；不支持将同一章拆到多集（但提示词内部会按场景切片，标「（略）」≠ 素材未使用）。来源映射代表素材已经过该集改编，不意味着每段原文都逐字保留。规划与编剧各一次模型调用，规划格式不合法可修复一次。真实戏剧质量仍需人工审阅。

核心服务：`core/drama_adaptation.py`（分集/交接）、`core/drama_context.py`（切片与预算）；存储：`core/drama.py`；Qt Worker 只负责模型调用适配、信号与取消。
