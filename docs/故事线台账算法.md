# 故事线台账算法（时间线 / 主线 / 支线 / 伏笔）

> 引擎路径：`src/novel_writer/core/story_threads.py`（纯 Python，无 Qt 依赖）
> UI：`src/novel_writer/ui/character/storyline_page.py`（世界菜单 → 故事线）
> 落盘：`data/projects/<项目>/story_threads.json`

## 一句话总结

把「规划稿种子」+「记忆流水」+「世界快照」对账成**一份带状态的线程台账**，
让作者在「世界 → 故事线」一屏看到：写到哪一章、哪些主线已完成、哪些支线在推进、
哪些伏笔该回收；并把台账摘要反哺回写作上下文。

> **单一写入方**：四类线程（时间线/主线/支线/伏笔）生成后，唯一可编辑来源是
> `story_threads.json`；`planning/` 下那四份稿只做首轮种子与归档，UI 不再展示、
> 正文/细纲/审校也不再回读。详见下文「单一写入方」。

## 与既有模块的分工（不重复造数据）

| 数据源 | 内容 | 在本模块中的角色 |
|---|---|---|
| `planning/{时间线,主线,支线,伏笔}.md` | 规划步骤生成的四份稿 | **种子**：仅首轮导入（或显式「重导入规划」）；之后归档、不再回灌 |
| `memory.json` → `open_loops` | 写后沉淀的未解伏笔 | **事实**：新伏笔入账、伏笔变「推进中」 |
| `memory.json` → `story_facts[伏笔回收]` | 已回收记录 | **事实**：把对应伏笔标 `done` 并补回收章 |
| `memory.json` → `subplots` | 四维追踪的支线进度 | **事实**：推进支线、写回收束章 |
| `world_state.json` → `timeline` | 实际发生事件 | **事实**：时间线节点标「已发生」，章号以正文为准 |

单向依赖：台账只读上述数据源，**不反向改 planning/memory**；手工编辑只写
`story_threads.json`，用 `user_edited` 字段保护，后续自动对账不覆盖。

## 单一写入方（2026-11-02）

之前「规划 9 份」里的 时间线/主线/支线/伏笔 与「世界 → 故事线」四类是同一套东西的
两个入口，两边都能改、再靠 `sync_from_planning` 对账，容易出现「规划稿改了但台账没变 /
台账改了下次同步又被规划稿覆盖」的拉扯。现在改成：

1. **生成**：`NEW_BOOK` 的 4 个规划步仍会写 `planning/{时间线,主线,支线,伏笔}.md`，
   作为一次性种子；规划页只展示 5 份文档（立意/大纲/章节细纲/人物设定/世界观）。
2. **首轮种子**：章循环开始前 runner 调一次 `sync_story_threads`，某类型**尚无**
   `source=planning` 条目时才解析对应归档稿；解析后不再自动回灌。
3. **每章自动推进**（核心）：章后 `chapter_digest` 的 `threads` 段给出本章推进/完成的主线、
   支线，`runner._sync_story_ledger` 调 `apply_thread_updates` 写回台账；伏笔由
   `memory.open_loops/resolved`、时间线由 `world_state.timeline` 对账推进。
   **整条链路不需要人工改台账**；`[THREADS]` / `[STORY]` 日志可观察。
4. **唯一编辑入口（可选纠错）**：需要人工介入时，在「世界 → 故事线」新增/修改/删除，
   全部写 `story_threads.json`；被手工改过的字段记 `user_edited`，后续自动推进不覆盖。
   正文、章节细纲、审校上下文只从台账取四类线（`build_context_block`）。
5. **不再回写伏笔稿**：`update_foreshadow` 移出默认模板；伏笔变化来自章后 digest/记忆对账
   与显式手工编辑。
6. **逃生口**：故事线工具栏 `⋯ → 从归档规划稿重导入…` 显式调用
   `sync_story_threads(force_planning=True)`，按归档稿重新解析并合并（`user_edited` 字段仍受保护）。
   日常「同步台账」只做记忆/世界状态对账，不碰归档稿。

### 章后自动推进（`threads` 段）

`chapter_digest` 在原有四段之外再产出：

```json
"threads": {
  "main":    [{"title": "拜入宗门", "status": "active|done"}],
  "subplot": [{"title": "感情线", "status": "active|done", "new": false}]
}
```

规则：

- `title` 必须与台账里的主线/支线标题逐字一致（提示词会把当前台账标题一起给模型）；
- **主线不新造**：匹配不到就忽略，避免模型编造主线；
- **支线可新开**：`new: true` 时新增一条（来源 `digest`），用于正文里自然长出的支线；
- `status=done` 时补 `chapters.resolve=当前章`；`active` 只改状态；
- `user_edited` 里的字段一律不覆盖；
- 没有 `threads` 段（旧 digest / 模型漏写）时，只是少一次显式推进，伏笔/时间线对账照常。

## 数据结构

```json
{
  "version": 1,
  "meta": {"planning_sigs": {"main": "mtime:size"}, "last_sync": "..."},
  "threads": [
    {
      "id": "sha256(kind:title)[:16]",
      "kind": "timeline | main | subplot | foreshadow",
      "title": "青霜剑剑灵",
      "detail": "第1章埋设，第20章回收",
      "status": "planned | active | done | abandoned",
      "planned_status": "规划稿里写的状态（区分计划回收/已回收）",
      "group": "第一卷：宗门风波",
      "owner": "",
      "location": "禁地",
      "chapters": {"plant": 1, "resolve": 20},
      "happened": true,
      "source": "planning | world_state | memory | manual",
      "active": true,
      "user_edited": ["status", "notes"],
      "notes": ""
    }
  ]
}
```

- `id` 由 `kind + title` 稳定哈希得出：规划稿重跑不会换 id，进度得以保留。
- `chapters.plant` / `chapters.resolve`：埋设（时间线=发生）章 / 回收（完成）章。
- `active=false`：规划稿里已删除的条目不物理删除（保留手工备注，可恢复）。
- `happened`：仅时间线用；`world_state.timeline` 命中或计划章已被写过 → true。

## 状态口径

| 状态 | 判定 | UI |
|---|---|---|
| `planned` 未开始 | 规划稿无状态词、章号在当前章之后 | 灰 |
| `active` 推进中 | 规划稿写「进行中/推进中/展开」，或已有埋设章 | 蓝 |
| `done` 已完成 | 规划稿写「已回收/已解决/已完成」，或记忆记录回收，**且回收章 ≤ 当前章**（无章号视为已确认） | 绿 |
| `abandoned` 已放弃 | 规划稿写「放弃/废弃/砍掉」 | 灰 |

**伏笔超期**是派生状态，不落盘：`未回收 && 当前章 - 埋设章 ≥ 15`（与
`memory.loop_urgency` 的 15 章超期线一致），UI 显示「超期 N 章」并标红。

**主线进度按里程碑算**：主线节点是「计划章写完即达成」，不要求人工标 done；
但规划里明说「进行中/推进中」、或有回收章且还没写到的，仍算未完成。
这样写了 50 章的项目不会永远停在 `0/35`（`StoryLedger.progress().main_done`）。

## 解析规则（规划稿 → 条目）

`parse_planning_doc(content, kind)` 兼容几种常见写法，宁可少解析也不把散文拆碎：

1. 列表项：`- 伏笔A（第3章埋，第12章回收）`；`1. 节点（第10章）`
2. 标题分组：`### 第1卷：宗门风波` 下的列表 → 分组名
3. 表格：按表头语义取列（伏笔/名称/节点 → 标题；埋设/起点 → plant；
   回收/揭晓 → resolve；状态/进度 → status；归属/人物 → owner）
4. 独立加粗行：`**节点名**`
5. **加粗小标题 + 同行说明**：`**转折一（第3章）**：首期榜单发布……`
   （LLM 写主线/时间线最常用的格式；标题里的「（第N章）」算埋设/发生章）
6. **加粗条目 + 后置字段行**：`**1. 首期好评扣分**` 下一行 `埋设：第30章`、
   再下一行 `回收：第39章` —— 续行会并入该条目，自动补 plant/resolve

补充规则：

- 父项带子列表且自身无详情 → 升级为分组（如 `- 感情线` + 缩进子项），子项归入；
  同级兄弟不继承该分组，回落到所属卷标题。
- 一级标题（`# 主线`）和通用名（伏笔/支线/时间线…）不当分组名。
- 标题长度 < 2 的行、说明性开头（说明/注/提示/总体…）跳过；
  卷首概括行（主线推进/核心事件/关键节点/本卷…）也不做成条目。
- 章号解析支持阿拉伯与中文数字：「第12章」「第十二章」「第12-15章」「12章」。
- 单份文档最多导入 300 条（`MAX_ITEMS_PER_DOC`）。

## 对账流程（`sync_story_threads(project_dir)`）

```
sync_from_planning(force=False)
  ├─ 按 mtime:size 判断四份文档是否变化（force=True 忽略签名）
  ├─ 新条目 → 新建线程；已有条目 → 只补空字段（user_edited 字段不动）
  ├─ 规划稿已删除 → active=False（软删除）
  └─ 记下每份文档签名

reconcile()
  ├─ memory.open_loops      → 伏笔入账/推进中（按标题或 subject 匹配）
  ├─ memory.story_facts[伏笔回收] → 对应伏笔 done + 回收章
  ├─ memory.subplots        → 支线推进/收束；规划里没有的即兴支线补入
  ├─ world_state.timeline   → 时间线节点 happened + 实际章号/地点
  ├─ 计划回收章已写过      → 伏笔 done（planned_status=done 时）
  ├─ 计划发生章已写过      → 时间线 happened（世界状态未必逐节点记录）
  └─ 人物/卷组为空          → 按标题角色名 + 章号所属卷补齐
```

对账是幂等的：重复执行不会产生重复条目，也不回退已完成状态。

## 字段联动（人物 / 卷组 / 回收章）

| 字段 | 数据来源 | 写入与使用 |
|------|----------|------------|
| 人物 `owner` | 角色注册表 + 世界状态角色 + `人物设定.md`；对账时从标题/详情里认名 | UI 可多选（`_OwnerPicker`）/手输；写作上下文以 `〔顾言、赵九衡〕` 附在线程标题后 |
| 卷组 `group` | 解析 `主线/大纲/时间线.md` 的「卷一…（1—100章）」标题 | 空值按「章号 → 卷区间」补齐；同一卷优先复用台账已有卷名；树上四类线程都按卷分组 |
| 回收章 `chapters.resolve` | UI 手填 / 标记完成时自动补 | 伏笔=回收章，主线/支线=完成章，时间线=结束章；标 `done` 时若为空，取当前写作章（时间线取发生章） |

`volume_ordinal()` / `parse_volume_ranges()` / `infer_owner()` 是纯函数，UI 与对账共用；
`StoryLedger.planning_volume_ranges()` 与 `known_character_names()` 给下拉框提供真实选项。
时间线在表单里按「发生章 / 结束章」展示，状态改 `done` 会同时写 `happened`，避免树上仍显示「计划中」。

## 反哺写作上下文

`StoryLedger.build_context_block(chapter)` 输出 ≤2.6K 字符的清单：

```
=== 故事线台账（反哺自规划/记忆/世界状态） ===
【主线进行中】…
【支线推进中】…
【待回收伏笔】⚠ 超期项标注「优先回收」
【时间线·最近已发生】…
```

注入位置：`ContextBuilder.build()` 中部参考区，仅对
`_STORY_LEDGER_STEP_IDS` 里的步骤注入：`chapter / chapter_outline / update_chapter_outline /
chapter_summary / summary / inspiration / pov_sim / review / review_panel / quality_check / sim`；
纯工具步骤（toc / fix_titles）不注入。

## 工作流联动（及时反哺）

| 触发点 | 动作 |
|---|---|
| 规划步骤（`ideation`…`foreshadow`）完成 | 进入「世界 → 故事线」或工作流结束时自动解析四份规划稿 |
| `world_state_update` 步骤完成 | **不再提前对账**（此时 memory 还没更新，等 sediment 后一次完成） |
| 每章写后沉淀（`sediment`）完成 | **每章唯一一次** `runner._sync_story_ledger(n)`：memory 伏笔/支线/回收 + world_state.timeline 一起进台账，并 `on_event("story_track")` |
| UI | `WorkflowThread.story_track` 信号触发故事线页刷新；工作流结束/停止/切换「世界」页也会对账 |

## 边界与注意事项

- **只读数据源**：台账不修改 planning/memory/world_state；要改规划请编辑规划文档。
- **手工优先**：UI 改过的字段进 `user_edited`，自动对账不会覆盖；想恢复自动逻辑可清空该字段。
- **章号是唯一时间轴**：所有进度都以「第 N 章」为准，不依赖日期字符串。
- **不是正典**：台账是视图/索引，`world_state.json` 与 `memory.json` 才是事实来源。
- **散文不解析**：规划稿写成大段散文时台账可能为空，这是有意的（避免噪声）。
