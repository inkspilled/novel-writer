# 整体重构建议

性质：计划。以下是下一阶段建议；除短剧跨章服务外，不代表已完成改造。

## 优先目标

让作者知道：下一步写什么、依据哪些事实、哪些生成结果已过期、失败后从哪里继续。保持本地创作与旧项目可用，按功能逐步替换，不一次重写全部代码。

## 1. 统一事实来源与修订

正文修订是事实依据；模型抽取是候选事实。为人物状态、物品归属、知识边界、时间线、伏笔记录稳定 ID、来源章/段落、修订号、证据、确认状态与有效章节区间。世界状态和故事线保留各自用途，作为统一事实的投影，避免独立生成后相互覆盖。允许人工确认与自动接受两种写作模式，并记录谁接受了变化。

优先抽出 `FactRepository` 与 `RevisionService`，再将现有 memory/world/canon/thread 写入入口集中到一个提交服务。正文仍用 Markdown；结构化元数据可逐步迁入 SQLite 事务，先做备份与导入校验，并保留可导出 JSON。

## 2. 以产物修订管理工作流

将“步骤 done”升级为“输入修订 + 模型/提示词版本 + 输出产物”。正文改动后，准确标记概要、事实、检索索引、分集、分镜等下游结果过期，不依赖作者猜测是否需要重跑。记录等待、运行、成功、失败、取消、过期状态；任务重试幂等，正文提交与事实沉淀应有明确的提交边界。

把现有 `runner.py` 的执行调度、`builtin_steps.py` 的业务操作、`context.py` 的材料选择分离为独立服务。新旧流程并存迁移，先覆盖“改一章→只重算受影响产物”的验收场景。

## 3. 检索以写作问题驱动

先读取本章目标、出场角色、地点和未决冲突，再形成多路查询。角色硬事实与知识边界按结构化记录精确查询，前文片段用 BM25 + 向量融合和重排。结果带章/段落出处、修订号与入选原因；提供“本次写作上下文”面板，支持作者移除错误材料。建立人标检索用例，测关键证据召回与未来信息泄漏，而非仅测字符串出现。

## 4. 正文生成分为可审阅阶段

先产出本章场景卡：目标、阻力、转折、代价、角色知道什么、如何承接上一章。再写正文；审稿只提出带引用的具体问题与局部修改建议。润色尽量保留事实与因果，不每次重写全章。规则分数用于发现长度、重复、格式异常；不能当作剧情好看的证明。用固定样章做盲评，分别评估因果、人物动机、承接和语言。

## 5. 短剧独立改编模型

已实现滑动窗口多章合一集、待用素材和失败恢复。后续把素材单位从“章”细化为带稳定 ID 的情节段，记录精确消费范围，支持半章顺延、单章拆多集。增加可编辑分集卡与改编决定（保留/压缩/合并/改写），先锁定集纲再写剧本。分镜、资产与视频提示词引用这些稳定来源，避免剧本变了下游仍被误认有效。

## 6. 界面以创作任务组织

保留“小说/短剧”两大模式，主界面突出正文或当前剧集。将当前任务、待处理问题、来源材料放在可收起侧栏；角色动画和工具日志作为辅助区域。空状态给出明确下一步，成本预估、停止状态、失败原因与可重试范围直接显示。短剧先展示分集列表、来源范围和待用素材，再进入剧本与分镜细节。

## 迁移顺序与验收

1. 修订号/来源映射/统一提交入口：旧项目无损打开，正文可回滚。
2. 工作流失效传播与恢复：修改第 N 章只重算受影响结果；失败不跳过未提交素材。
3. 检索证据与固定评测集：答案能追溯原文，角色知识不越界，不混入未来章节。
4. 场景卡与局部修订：作者能预览、接受或拒绝修改，并对照旧稿。
5. 段落级短剧改编与界面调整：消费范围不遗漏、不重复，半章顺延可恢复。

暂不优先增加智能体数量、供应商数量、复杂自治推演或视频一键生成。先用可追溯的事实与可恢复的工作流支撑创作。
