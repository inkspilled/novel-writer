## 0. 一句话结论

**现在的代码结构上吃不到 1M 的缓存红利**：最该被复用的「前文」被放在每次都变的前缀之后，缓存从第一个变化点就断了；而且**命中率目前无法统计**——usage 只留两个字段，正文走流式连 usage 都没有。

1M 的正确用法不是「多塞」，是「**稳定前缀 + 尾部增量**」；「上下文满」应该由预算和命中率定义，而不是由窗口定义。

## 1. 名词与前置事实

### 1.1 本文用到的三个词

| 词 | 含义 |
|---|---|
| **前缀缓存** | 供应商把请求开头的一段 token 缓存起来，下次请求**从第 0 个 token 起的最长公共前缀**命中则按折扣价计费。只要中间有一个 token 变了，其后全部失效 |
| **缓存命中率** | 命中 token ÷ 总输入 token。本文区分三种口径，见第 8 章 |
| **前缀保持** | 压缩/裁剪时只动尾部，不动已命中前缀的中间。本文的核心约束 |

### 1.2 主流厂商机制对照（公开文档口径，接入前需按实际厂商复核）

| 厂商 | 触发方式 | 最小/粒度 | 命中字段 | 写入字段 | 单价量级 |
|---|---|---|---|---|---|
| DeepSeek | **自动**，无需标记 | 64 token / 64 | `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 无（写免费） | 命中 ≈ 未命中 × 0.1 |
| OpenAI | **自动** | 1024 / 128 | `prompt_tokens_details.cached_tokens` | 无 | ×0.1–0.5（按模型） |
| Anthropic | **显式** `cache_control` 断点（≤4 个） | 1024（Sonnet/Opus） | `cache_read_input_tokens` | `cache_creation_input_tokens` | 读 ×0.1，写 ×1.25 |
| 通义 / Kimi / GLM | 多为自动 | 视厂商 | 字段名不统一（常见 `cached_tokens`） | 视厂商 | 视厂商 |
| Gemini | 自动 + 显式 CachedContent | 视模型 | `cachedContentTokenCount` | — | 视模型 |
| Ollama / vLLM / llama.cpp | 无计费缓存 | — | 无 | 无 | 只影响延迟（KV cache） |

**这张表决定了两条不同技术路线**：DeepSeek/OpenAI 只要「前缀排好」就自动生效；Anthropic 还要「在正确的位置打断点」。

### 1.3 一个重要推论

长上下文的经济性 = **前缀复用次数 × 前缀长度**。

- 500K 输入只调一次，比 50K 贵 10 倍；
- 同样 500K 被复用 20 次且命中价 0.1x，单次有效成本 ≈ `500K × 0.1 + 新增`。

所以：**没有缓存，1M 根本用不起；只做缓存不把前文从 2 章扩到 20–50 章，收益又小到看不见。两件事必须一起做。**

## 4. 现状体检（可核对的事实）

> 每条都给「证据 + 复核方式」。这是本文最应该被逐条验证的部分。

### F1. 消息布局是缓存杀手

**证据**：[base.py:88-98](src/novel_writer/core/agents/base.py#L88)

```python
system_parts = [self.config.system_prompt]
if context:
    system_parts.append(context)          # ← 20K 可变内容进 system
system_content = "\n\n".join(system_parts)
history = self._trim_history(self.history)
messages = [LLMMessage(role="system", content=system_content)]
messages.extend(history)                  # ← 排在可变内容之后
messages.append(LLMMessage(role="user", content=user_input))
```

**影响**：`context` 每章每步都变，它一变，后面的 `history` 和 `user` 全部不可命中。理论命中上限 ≈ `system_prompt` 长度 ÷ 总 prompt 长度，**约 5%–10%**。

**复核**：`git grep -n "_build_messages" src/` 看调用点；或打印一次真实请求的 messages 数组。

### F2. 每个步骤各有一套前缀，章内也无法共享

**证据**：[context.py:184-222](src/novel_writer/core/workflow/context.py#L184) 的 `STEP_CONTEXT_TIERS`：`chapter`=WORKING、`polish`=NARRATIVE、`proofread` 走短路只放当前章、`sim`=WORLD。

**影响**：同一章 5–8 次调用，前缀几乎全不同。即使不考虑跨章，**章内第 2 次调用也命中不了第 1 次**。

**复核**：对照 [definition.py:167-191](src/novel_writer/core/workflow/definition.py#L167) 的 `_CYCLE_STEPS`，统计每章实际会跑哪些步骤。

### F4. 流式调用完全没有 usage（正文写作隐形）

**证据**：抽象签名 [llm/base.py:65-79](src/novel_writer/core/llm/base.py#L65) 是 `AsyncIterator[tuple[str, str]]`，结构上返回不了 usage；实现 [client.py:430](src/novel_writer/core/llm/client.py#L430) 也没读最后一个 chunk 的 usage；runner 里流式结束后直接 `LLMResponse(content="".join(parts))`（[runner.py:751](src/novel_writer/core/workflow/runner.py#L751)）。

**旁证**：`logs/info.log` 里 `agent=writer` 的完成记录共 8 条，`usage` **全部为 `{}`**；而真实写作走 `stream_run`（[base.py:220](src/novel_writer/core/agents/base.py#L220)），该函数**连一条日志都不打**。两种情况合起来：正文 token 无论如何都进不了统计。

**影响**：`total_usage` 少算整章正文的输出 token 与全部输入 token；成本审计和工作流条的数字**系统性偏低**。

**复核**：跑一章，观察工作流条 token 与供应商后台账单的差异。

### F5. 48K 预算是「拍脑袋值」，与模型脱钩

**证据**：[context.py:41](src/novel_writer/core/workflow/context.py#L41) 硬编码 `MAX_CONTEXT_TOKENS = 48_000`；UI 允许 4096–1,000,000（[model_dialog.py:80](src/novel_writer/ui/settings/model_dialog.py#L80)），存全局配置（[workflow_mixin.py:204](src/novel_writer/ui/app_shell/workflow_mixin.py#L204)）。

**实测**：日志里 planner / reviewer 的真实 `prompt_tokens` 为 **5,678 / 13,196**；短剧侧 6,654–15,971。**1M 窗口只用了约 0.6%–1.6%。**

**影响**：调大预算只会让更多材料进 prompt，在现有布局下等于直接加钱；调小又会让压缩频繁触发、前缀反复被改写。

### F6. 压缩会改写块的中间，一触发前缀全碎

**证据**：[context.py:88-97](src/novel_writer/core/workflow/context.py#L88) 阶段一用 `_shrink_rag_block` / `_truncate_block`（[context.py:142](src/novel_writer/core/workflow/context.py#L142)）**原地截断**块内容。

### F10.（附加发现）`other` 类永不裁剪，预算对某些步骤失效

**证据**：`compress_context` 的类型判定（[context.py:64-77](src/novel_writer/core/workflow/context.py#L64)）；`polish` 的整章正文块标记是 `=== 当前章节正文（全文，待润色） ===`，**不匹配任何类型，落入 `other`**，而 `other` 两级都不裁。

## 6. 收益测算（**未验证**，请重点挑战）

### 6.1 假设（每一条都可以被推翻）

| 编号 | 假设 | 若为假的后果 |
|---|---|---|
| A1 | 平均 ≈ 4K **真实** token/章（样本每章 3.3K–8.4K 字 × 0.65–0.8 token/字，均值 ≈ 3.9K） | 所有容量/成本数字同比例偏移 |
| A2 | 命中价 = 未命中的 **0.1 倍**（DeepSeek 量级） | 收益按比例缩水 |
| A3 | 每章 5 次有效 LLM 调用（正文/润色/抽取/校对/摘要，部分有 `every` 间隔） | 收益按比例变化 |
| A4 | 章尾可变区 ≈ 25K 真实 token | 同上 |
| A5 | 布局改对后命中率可达 **90–95%**（append-only 卷宗） | 这是**目标值，不是预测值**；见 H4 |
| A6 | 1M 窗口按 0.5 折使用（安全边际 + 注意力） | 容量上限变化 |

> ⚠️ 项目自己的 `estimate_tokens` 是 `汉字 × 1.5 + 英文单词 × 1.3`（[context.py:29](src/novel_writer/core/workflow/context.py#L29)），对中文**可能高估约 2 倍**（见 H2）。所以「48K 预算」对应的真实量可能只有 ~22K。**在 H2 验证前，本文一律用「真实 token」口径，不与项目估算混用。**

### 6.2 三档卷宗的成本量级

按 A1–A5，单章 5 次调用：

| 卷宗深度 | 前缀 tokens | 单次输入 | 单次有效计费 | 单章有效计费 | 相对现状 | 拿到的前文 |
|---|---|---|---|---|---|---|
| 现状（近 2 章全文，无稳定前缀） | 0 | 25K | ~24K | ~120K | 1.0× | 2 章 |
| 10 章 | 40K | 65K | 4K + 25K = 29K | ~145K | 1.2× | 10 章 |
| 30 章 | 120K | 145K | 12K + 25K = 37K | ~185K | 1.5× | 30 章 |
| 50 章 | 200K | 225K | 20K + 25K = 45K | ~225K | 1.9× | 50 章 |
| 100 章 | 400K | 425K | 40K + 25K = 65K | ~325K | 2.7× | 100 章 |

**对读法**：50 章卷宗比现状贵 1.9 倍，但前文量是 25 倍。同样 50 章**不做缓存**则是 `225K × 5 = 1.1M`，是现状的 9 倍——**缓存把「9 倍」压成「1.9 倍」**。

### 6.3 什么时候会撞满 1M

- 按真实 token（4K/章）：**约 250 章**
- 按项目估算口径（8.4K/章）：**约 120 章**

一本 500 章的书**必然撞满**，所以「压缩纪元」（见 9.4）必须从第一天就设计，不能等报错。

### 6.4 收益的另一个来源：延迟

300K 前缀未命中时，prefill 可能 30–60s；命中后首字延迟显著下降。对「点开一章等 40 秒」的体验是质变。**这一项比省钱更重要，但本文没有量化数据**（见 H7）。

## 7. 目标布局：把 prompt 当「前缀树」，不是拼字符串

### 7.1 分层

```
┌─ L0 静态身份 ───── system_prompt + 项目元信息 + 硬约束          ~1–2K    终生不变
├─ L1 圣经 ───────── 人物设定 / 世界观 / 大纲 / 细纲             ~10–30K  update_* 时才变
├─ L2 定稿卷宗 ───── 已封印章节原文 + 结构化概要（append-only）   10 章≈40K  只追加
├─ L3 会话历史 ───── 规划链传递用（可丢弃）                       ≤24K     排在卷宗之后
├─ L4 本章可变区 ─── 近章全文 / 活性卡 / 伏笔 / RAG / 灵感        ~10–20K
└─ L5 任务指令 ───── 步骤 prompt + 尾部警示复述
```

### 7.2 落到消息数组（**保持单条 system**，兼容 Qwen 等要求单一 system 的模板）

现状代码的注释明确写了「兼容 Qwen 等要求单一 system 的模板」（[base.py:89](src/novel_writer/core/agents/base.py#L89)），所以**不要拆成多条 system**：

```
[system]  L0 + "\n\n" + L1 + "\n\n" + L2        ← 单条，稳定前缀
[history] 规划链才需要，章循环可关
[user]    L4 + "\n\n" + L5                       ← 每次变化的部分
```

`L2` 追加新章时，**system 消息的前 N 个 token 不变**，前缀依然命中；只有新追加的尾巴是新的。这正是 append-only 的价值。

> Anthropic 走另一条路：`cache_control` 要打在 **content block** 上，需要把 system 拆成多个 block（不是多条 message），在 L0/L1/L2 末尾各打一个断点（≤4 个）。这是 `claude.py` 的独立实现分支。

### 7.3 三条设计规则

**R1：L2 只追加，永不改写。**
已封印章节按章号顺序拼接；新章接在末尾。命中率**随书变长而上升**——这是长篇最想要的性质。

> 前提：只把**已封印**章节放进 L2。`seal_chapter` 排在 `polish` 之后（[constants.py:16-21](src/novel_writer/core/workflow/constants.py#L16) 的顺序 + `_write_output` 对 `is_sealed` 拒写），所以卷宗天然不可变。
> 反例：用户**手工编辑**已封印章节，会让该章之后的所有缓存失效——需要版本号标记或 UI 提示，否则命中率会莫名其妙掉下去。

**R2：history 必须降级到可变区。**
只要 history 排在 append-only 段前面，它一变，整段卷宗全废。「history 与长前缀不可兼得」是绕不过的取舍：规划链单独用一个短前缀 profile，章循环直接关历史（顺带修 F9 的重复注入）。

**R3：字节级确定性。**
同章同步骤跑两次，L0–L2 必须 byte-identical。这条要写成单测，否则 `dict` 顺序、`set` 迭代、RAG 排序任一抖动都会**静默**吃掉命中率。验收方式：对 L0–L2 取 `sha256`，两次相等。

### 7.4 为什么不能只改 `compress_context`

因为压缩发生在**组装之后**（[context.py:377](src/novel_writer/core/workflow/context.py#L377)），它看到的是已经拼好的字符串，只能按前缀文本猜类型、原地改写。要满足「前缀保持」，压缩必须知道**段的边界和稳定性等级**——所以 `ContextBuilder` 必须先返回结构化的 `segments`，压缩器再按「从最不稳定的段开始整段丢弃」工作。

## 8. 命中率怎么统计

### 8.1 三个口径，缺一不可

| 指标 | 定义 | 回答什么问题 |
|---|---|---|
| 报告命中率 | `cached / total_input` | 省了多少钱 |
| 可缓存上限 | `最长公共前缀 tokens / total_input` | 布局的理论上限 |
| **缓存效率** | `实际命中 / 可缓存上限` | **布局有没有被破坏**（唯一能定位问题的指标） |

只报第一个，永远吵不出结论：命中率低可能是「布局差」，也可能是「网关没回字段」。

### 8.2 归一化（**最容易出错的地方**）

| 厂商 | `total_input` | `cached` | `cache_write` |
|---|---|---|---|
| DeepSeek | `prompt_tokens` | `prompt_cache_hit_tokens` | 0 |
| OpenAI | `prompt_tokens`（**含** cached） | `prompt_tokens_details.cached_tokens` | 0 |
| Anthropic | `input_tokens + cache_read + cache_creation` | `cache_read_input_tokens` | `cache_creation_input_tokens` |
| 兼容层 | 视字段探测 | `cached_tokens` 等 | 视厂商 |
| 本地 | `prompt_tokens` | 0 | 0 |

不归一化，会算出 >100% 或负数命中率，然后没人信这个数。

**数据质量标记**：若响应里没有任何缓存字段，记 `cache_meta_present=false`，与「真的没命中」区分开。

### 8.3 诊断靠「指纹 + 首异点」

每次调用记：

```python
prefix_fingerprint = sha256(model + tool_schema + serialize(messages_prefix)).hexdigest()
```

与同 `(agent, model, profile)` 的上次比：

- 指纹相同、`cached=0` → 供应商没缓存 / TTL 过期 / 中转网关丢字段（**环境问题**）
- 指纹不同 → 记 `diverged_at=<segment_id>`（第一个不同的段），**直接指出是哪一段劈了缓存**

没有这个，命中率低了只能猜。

### 8.4 落盘与展示

**落盘**（与 [journal.py](src/novel_writer/core/workflow/journal.py) 同目录同风格，追加到 `runs/usage.jsonl`）：

```json
{"ts":1763100000.123,"event":"llm_call","run":"20261114-171602-1234-新书全流程",
 "step":"chapter","n":12,"agent":"writer","model":"deepseek-chat",
 "prompt":24831,"completion":3920,"cached":0,"cache_write":0,
 "cache_meta_present":true,"est_tokens":41200,
 "fingerprint":"a1b2…","diverged_at":"L2:chapter_11","duration_s":41.2}
```

**展示**（[workflow_bar.py:168](src/novel_writer/ui/workflow/workflow_bar.py#L168) 现在只显示 `12.3k tok`）：

```
12.3k tok · 命中 62% · 效率 79% · 可缓存 78%
```

### 8.5 验收标准

1. 单测：5 家样例 usage JSON → `normalize_usage` 输出符合 8.2 表。
2. 单测：流式最后一个 chunk 的 usage 能被解析并回传。
3. 单测：同章同步骤两次 `build`，L0–L2 的 `sha256` 相等。
4. 集成：离线模拟器在 20 章样本上的预测命中率，与实跑 3 章的实测值误差 < 10%。

## 9. 「上下文满了」怎么处理

### 9.1 先把「满」拆成三个阈值

| 阈值 | 含义 | 现状 |
|---|---|---|
| `window_limit` | 模型硬窗口（如 1M） | 完全没建模 |
| `budget_limit` | 成本 / 延迟预算（**真正该管的**） | = 48K，与模型脱钩（F5） |
| `quality_limit` | 注意力稀释阈值（lost in the middle） | 只有「U 形布局」经验，无数据 |

**核心认知：1M 模型下「窗口满」很少发生，先撞到的是账单和延迟。** 所以日常要管的是 `budget_limit`，`window_limit` 只做兜底。

### 9.2 前缀保持原则（新约束）

> 任何裁剪只能动尾部，**不能动已命中前缀的中间**。

这条把压缩的目标函数从「最小 token」变成「**最小 token 且前缀不动**」。现有 `compress_context` 完全不满足（F6）。

### 9.3 四级降级

| 级别 | 动作 | 前缀影响 |
|---|---|---|
| 1 | 裁可重建的尾部：RAG 片段 → sim → 近章全文 → 活性卡 | 无（都在 L4/L5） |
| 2 | 降级本章可变区：近 2 章全文 → 近 1 章 → 只用摘要 | 无 |
| 3 | **压缩纪元**：旧章 → 事件摘要，重建卷宗快照，`layout_version+1` | **一次计划内全量 miss** |
| 4 | 溢出兜底：捕获 400，尾部整段丢弃后重试一次 | 无 |

**关键改动**：级别 1 必须是**整段丢弃 / 整段保留**，禁止 `_truncate_block` 那种块内改写。要缩量就在**组装时**按预算取更少的内容，而不是事后剪字符串。

### 9.4 压缩纪元（epoch）

- 触发：章节数超过阈值（如 200 章）或 L2 超过预算的 2/3。
- 动作：把「最近 K 章」之外的原文压成「卷宗摘要」（每 10 章一份，带人物/伏笔/事件指纹），生成新的 L2 快照，bump `layout_version`。
- 代价：一次全量 miss（可预算，例如每 200 章一次）。
- **不可省略**：500 章的书必然撞满 1M（见 6.3）。

### 9.5 溢出兜底（F7 的修复）

```python
except BadRequestError as e:
    if is_context_overflow(e):        # 状态码 400 + 关键词/错误码
        messages = drop_tail_blocks(messages, keep=...)   # 只丢 L4/L5
        log_to_journal("context_overflow", step, dropped=[...])
        return await retry_once(messages)
    raise
```

并把 `context_overflow` 写进 journal，下次同步骤预检就少放，形成闭环。

### 10.2 按前缀分组调度（容易被忽略的收益）

同一前缀组的步骤应该**背靠背跑**，第一个跑的是「预热者」，后面白嫖：

```
chapter（预热 L0–L2 + 本章）
  ├─ polish        ← 复用
  ├─ chapter_digest← 复用
  ├─ proofread     ← 复用
  └─ chapter_summary
```

现在这五个步骤各自组装、各自跑，前缀不同（F2），**一次都共享不了**。Anthropic 5 分钟 TTL 尤其要求背靠背。

### 10.3 工具 schema 归一（F8）

`toolkit.build(step.tools)` 每步不同 → 前缀不同。两个选项：

- **A（推荐）**：全步骤使用同一套 superset schema，用 prompt 指令限制「只在缺事实时调用」。
- **B**：保持每步子集，但**固定子集的枚举顺序**，并接受该步骤无法与其它步骤共享前缀。

### 10.4 与现有开关的冲突

| 开关 | 现状 | 冲突 |
|---|---|---|
| `rotate_agents` | 默认关（[runner.py:92](src/novel_writer/core/workflow/runner.py#L92)） | 开启会轮换 system_prompt，**与缓存天然冲突**；保持默认关 |
| `fast_model` | `sim`/`summary`/`digest` 走快模型 | 不同 model = 不同缓存域，统计要按 `(model, agent)` 分开 |
| `enable_tools` | 默认开 | 关闭后工具块消失，前缀与开启时不同 |

### 10.5 断点续跑

`runs/prefix_state.json` 记录每个 `(agent, model, profile)` 的上次指纹。resume 时能判断「这次还能不能命中」，并在 UI 上提示「本次续跑预计命中 X%」。

## 11. 反方观点（先替评审把最强的反驳说出来）

**反方 1：「收益太小，不值得改。」**
按 6.2，现状 48K 预算下即便命中到 95%，每次也就省 ~2K token，绝对金额很小。**这条是对的，也是本文最容易翻车的地方。** 回应的前提是「同时把前文从 2 章扩到 20–50 章」；如果只做缓存不扩上下文，ROI 确实接近 0。**所以本文的成立依赖于产品上要不要「更长的前文」。**

**反方 2：「长上下文会降低质量。」**
有 lost-in-the-middle 证据，现有 U 形布局（头尾高注意力）只解决了一部分。50 章原文灌进去可能让模型抓不住重点。**这是最大风险，必须 A/B 验证（H5），不能靠直觉。**

**反方 3：「改动风险大于收益。」**
F1/F2 动的是**所有步骤的所有调用**，改错一次全流程崩。缓解：P0 只加观测不改行为；P1 加开关（`prompt_layout: legacy|segmented`），可一键回退。

**反方 4：「供应商不支持 / 中转网关丢字段。」**
很多用户走中转，`prompt_tokens_details` 可能不返回。**这会让命中率永远显示 0，比不做更误导。** 缓解：`cache_meta_present` 标记 + 指纹效率指标（即使没有 cached 字段，也能用「前缀是否稳定」判断布局质量）。

**反方 5：「1M 模型本身就不该用。」**
如果目标是「稳定出稿」，128K + 更好的摘要/记忆系统可能比 1M 更便宜更稳。**本文不主张一定要上 1M**，只主张「如果要上 1M，必须先把前缀排好」。
