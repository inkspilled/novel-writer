# 大世界状态算法

> 引擎：`src/novel_writer/core/world_state.py` → `WorldState`
> 落盘：`{project}/world_state.json`
> 调用点：上下文组装 Tier 1、工作流内置步骤 `world_state_update`、写后 LLM 结构化更新
> 测试：`tests/test_world_relations.py`、`tests/test_story_threads.py`

## 一句话总结

像游戏存档一样追踪小说世界的结构化数据（世界/角色/物品图鉴/时间线），支持 LLM 返回的结构化 JSON 增量更新，并生成注入 LLM 的文本摘要。与 [长期记忆](长期记忆算法.md) 互补：**world_state 存「当前快照」，memory 存「变化历史」**。

## 数据结构

```json
{
  "version": 1,
  "world": {
    "name": "青云修仙界",
    "current_date": "宗历1247年 秋",
    "locations": {"禁地": {...}},
    "power_system": {"levels": ["炼气", "筑基", "金丹", ...]}
  },
  "characters": {
    "凌尘": {
      "cultivation": {"level": "炼气", "sub_level": "二层"},
      "hp": 100, "sp": 30, "gold": 5,
      "goals": ["查清灵脉", "保护苏婉"],
      "inventory": [{"name": "青霜剑", ...}],
      "equipment": {"weapon": "青霜剑"},
      "skills": ["基础剑法"],
      "location": "杂院"
    }
  },
  "items_catalog": {
    "青霜剑": {"type": "武器", "effect": "冰系攻击", "durability": "...", "uses": -1, "life_save": false}
  },
  "timeline": [
    {"chapter": 1, "event": "...", "location": "..."}
  ],
  "location_log": [
    {"chapter": 1, "date": "宗历1247年 秋", "character": "凌尘",
     "action": "enter", "location": "药圃", "from": "杂院"}

```

## 核心 API

| 方法 | 语义 |
|------|------|
| `load() / save()` | JSON 读写，失败回退 `_default_state()` |
| `add_location / set_date` | 世界层 |
| `get_character / add_character / update_character` | 角色层；update 走 `_deep_merge` |
| `add_item / get_item / give_item / remove_item` | 物品层（图鉴 + 角色背包） |
| `record_location_event(chapter, character, action, location, from)` | 地点流水（enter/leave，上限 2000 条） |
| `add_location / referenced_locations / sync_locations` | 地点实体与补全 |
| `characters_at / items_at / set_item_position` | 按地点反查在场角色/地面物品、改物品位置 |
| `query_location_log(character, location, start, end, limit)` | 按人物/地点/章号范围查地点流水（JSON 内过滤，默认最近 200 条） |
| `add_timeline_event(chapter, event, location)` | 时间线追加（章号强制转 int） |
| `compact_update(update_json, chapter)` | 把 LLM 全量快照压成最小 diff（写正典前调用） |
| `apply_llm_update(update_json, chapter)` | 结构化更新入口 |
| `build_context_text()` | 生成注入 LLM 的文本摘要 |

### 深度合并（`_deep_merge`）

`update_character` 的嵌套 dict 递归合并，叶子值覆盖。典型：

```python
ws.update_character("凌尘", {"cultivation": {"level": "炼气", "sub_level": "三层"}})
# 仅覆盖 sub_level，hp/gold 等其余字段保留
```

### LLM 结构化更新（`compact_update` → `apply_llm_update`）

LLM 先输出一份「全量快照」，`compact_update` 再压成最小 diff，避免把没变化的字段写进正典：

- `characters`：只保留变化字段；`inventory` 改写成 `inventory_add` / `inventory_remove`
- `items`：`new` 丢弃已存在的；`give/remove/move` 只保留实际变化
- `locations`：与当前一致的丢弃
- `timeline`：按 event 去重 + 截断（默认最多 3 条）
- `date`：与当前一致则丢弃

`apply_llm_update` 识别的键是：`characters` / `items`（`new` / `move` / `give` / `remove`）/
`locations` / `timeline` / `date`（**不是** `items_catalog` / `world`）。角色更新走 deep merge；
角色位置变化会自动写 `location_log`（先 leave 旧地点、再 enter 新地点）；时间线章号以本次
`chapter` 为准，LLM 漏传也不会落 0 章。

### 角色档案同步（`CharacterRegistry`）

`world_state.characters` 是 **location / goals / state 的事实来源**；`canon/characters.json`
里的同名角色档案是给 POV 推演/离场 tick 用的镜像：

- `world_state_update` 写盘后调用 `CharacterRegistry.sync_from_world_state(gs)`，
  把位置、目标、状态同步进档案；
- 「世界 → 人物」页打开/刷新时也会同步；作者手改位置/目标后保存会
  `push_to_world_state()` 回写，避免两套数据各说各话；
- 只同步非空字段，世界状态尚未记录时不会清掉作者手填值。

### 上下文文本（`build_context_text`）

输出世界名/时间/等级体系 + 地点流水（近 8 条）+ 角色摘要（境界/生命/灵石/位置/背包/技能）+ 物品图鉴。上下文组装 Tier 1 走的是更精简的 `world_brief` + `build_merged_character_states`（见[分层上下文组装算法](分层上下文组装算法.md)），并非此全量函数。

## 与长期记忆的分工

| 维度 | world_state | memory |
|------|-------------|--------|
| 形态 | 当前快照（可覆盖） | 变更流水（outdated 审计） |
| 角色数据 | 结构化字段（境界/hp/背包） | 状态变化句（`X突破`） |
| 写入方 | LLM 结构化更新 / UI | 正则沉淀 / 四维追踪 |
| 上下文 | Tier 1 角色状态（优先） | Tier 1 补充 + Tier 2 伏笔 |

`build_merged_character_states` 合并规则：**world_state 有的角色以其为准**，memory 中独有角色再补充，按名字去重。

## 边界与已知限制

- `remove_item` 等物品操作依赖角色 `inventory` 为 `list[dict]`，手改 JSON 时需保持结构。
- `apply_llm_update` 对 JSON 格式敏感（需合法 JSON），LLM 输出带解释文字时会失败——调用方需先抽 JSON 块。
- `add_timeline_event` 本身只追加；去重由 `compact_update` 在写正典前完成，直接调 `apply_llm_update` 时不会自动去重。
- `build_context_text` 与 Tier 1 的 `world_brief`/`build_merged_character_states` **输出口径不同**，勿混用。
- `location_log` 只记录「角色 location 字段变化」；手工改 `characters.*.location` 不走 `apply_llm_update` 时不会自动补流水（UI 手改只回写当前位置，不伪造章节流水）。
- `location_log` 存在 `world_state.json` 内，上限 2000 条，适合单机叙事规模；若需要跨人物/地点/章号的高频组合查询或超过数万条，再迁移到 SQLite/JSONL，见[项目存储与文件格式](项目存储与文件格式.md)「流水账选型」。
