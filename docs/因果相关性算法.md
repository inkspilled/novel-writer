# 因果相关性算法

> 引擎：`src/novel_writer/core/memory.py`（`loop_urgency`）+ `src/novel_writer/core/workflow/context.py`（`ContextBuilder`）
> 调用点：每章动笔前组装上下文时（`ContextBuilder.build`）+ 写后沉淀时机（runner `_run_sediment`）
> 落盘：紧急度为**读取时动态计算**，不落盘；沉淀时机由 `workflow.json` 的 `sediment_{n}` 断点键跟踪
> 测试：`tests/test_workflow_runner.py`（`TestLoopUrgency` / `TestAttentionTail` / `TestSediment`）

## 一句话总结

「哪些记忆要进本章上下文」**不是一个全局算法，而是四路确定性信号各管一个时间尺度**：近章靠窗口、本章相关实体靠大纲命中、跨章因果靠台账紧急度、远章长尾靠检索兜底——目标是让「所有与本章有因果关系的记忆」被照顾到，而不是「所有记忆」都进上下文。

## 为什么不是「所有记忆都塞进去」

第 100 章通常只需要：最近 2 章的承接 + 本章出场角色的当前状态 + 若干个该收的伏笔。把前 99 章全文塞进去有两个问题：token 成本线性爆炸；更糟的是**注意力稀释**——50 章前的关键伏笔反而会被淹没。因果相关性的判断标准因此是「这条记忆是否影响本章的连贯性」，而影响只来自四个通道，各通道用确定性规则即可判断，不需要学习算法。

## 四路信号

| 信号 | 时间尺度 | 实现位置 | 注入位 |
|------|----------|----------|--------|
| S1 时近性 | 最近 2 章全文 / 5 章概要 / 滚动摘要（每 5 章） | `_add_working_memory` | 中部 |
| S2 实体重叠 | 本章 | `_extract_chapter_entities`：大纲本章描述段中子串命中 world_state 角色/地点名 → 拉活性记忆卡 | 头部（高注意力） |
| S3 因果台账 | 埋设→回收的跨章跨度 | `open_loops` 动态紧急度排序 + 超期标记；`info_boundary` 信息边界；`story_facts` 已回收清单防复收 | 尾部（高注意力） |
| S4 检索兜底 | 全史 | BM25 top-5（查询 = 大纲第 n 章描述段） | 中部 |

四路各自的失效模式与互补关系：S1 管不了 20 章前的伏笔（S3 接住）；S2 认不出别名/绰号（S4 概率性兜底）；S3 的台账质量取决于沉淀质量（见[写后沉淀算法](写后沉淀算法.md)边界）。

## 伏笔动态紧急度（`loop_urgency`）

埋设时 `payload.urgency = 0.6` **仅作静态回退**（`current_chapter<=0` 时用）；进入写作循环后按当前章号**动态重算**，不采用 payload：

```
urgency = clamp( 0.3 + min(0.6, 埋设后经过章数 × 0.03) + 阶段加成 , 0, 1 )

阶段加成：剧情进度 ≥ 60%（收束期）  +0.15
          剧情进度 ≥ 90%（终章阶段）+0.30
超期判定：urgency ≥ 0.75 → 尾部标注「已超期，本章优先回收」
```

设计意图：

- **刚埋的伏笔不催收**：3 章内 urgency ≈ 0.3–0.4，排序沉底；
- **年龄线性上涨，20 章饱和**：15 章未收即达超期线 0.75（一部 100 章的书，一个坑 15 章不填读者已经忘了）；
- **阶段加成对齐节奏控制**：与[节奏控制与角色锚定算法](节奏控制与角色锚定算法.md)的反哺/写作阶段划分一致——收束期要求「逐步回收」、终章阶段要求「全部解决」；
- `current_chapter <= 0` 时退化为静态 urgency（兼容旧调用）。

排序在 `MemoryScratchpad.get_open_loops(limit, current_chapter, total_chapters)`，展示（含超期标记）在 `ContextBuilder._build_attention_tail`。

## 近期已回收清单（防复收）

`close_loop` 会把伏笔标记 outdated 并在 `story_facts` 写一条 `aspect=伏笔回收` 的记录。尾部注入近 8 章的回收记录（最多 4 条），明确告诉模型「这些坑已经填了，不要重复回收、不要把解开的谜再挖开」。outdated 项不进未解清单，但模型也需要正反两个方向的信号。

## 沉淀时机（接受后入账）

因果台账的输入是记忆，记忆的输入是正文——**什么时候从正文提取记忆，决定台账的可信度**：

```
第 n 章循环：chapter 写正文 → chapter_summary → world_state_update → toc
           → polish（每 2 章，会改写正文！）→ proofread → summary/反哺（每 5 章）
           → ★ sediment（全部章后步骤完成后，从最终落盘正文提取）
```

- 沉淀放在**全部章后步骤（含润色）之后**、读取最终落盘文件而非 LLM 原始输出——草稿不是正典，润色前的文本不入账；
- 断点键 `sediment_{n}`：失败不标记、恢复时自动重试，成功后不重复提取（幂等）；
- 章节文件查找排除 `.bak.txt` 备份（`_CHAPTER_RE` 负向断言），备份里的旧文本永不入账。

## 与压缩预算的关系

四路信号都进上下文后，`compress_context` 按优先级整段裁剪（RAG → 旧章全文 → 规划文档 → 推演 → 概要，见[分层上下文组装算法](分层上下文组装算法.md)）。**头部活性记忆卡和尾部台账永不裁剪**——高注意力区的内容必须小而准，这正是四路信号宁可各管一段、不做全量注入的原因。

## 边界与已知限制

- S2 实体重叠是子串匹配：别名、绰号、称呼变化不命中（后续方向：embedding 召回补足，BM25 作回退）。
- S3 台账质量取决于沉淀质量：已由 **LLM 沉淀主通道**接管（铁律「假设不是事实」，伏笔按 subject 精确回收）；正则只作兜底，噪声仅出现在 LLM 不可用时。`reader_promises/relationships/world_rules` 已接线（LLM 写入，尾部/中部读取）；`timeline` 由 world_state_update 的快照更新负责。
- `target_chapters` 缺失时（老项目/未设目标），阶段加成不生效，只剩年龄项。
- token 估算是启发式（±30%），压缩触发点有误差但方向正确。
